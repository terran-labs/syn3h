## Matrix contract

The default matrix contains fifteen cells: lobby, spawn, water, mixed bots and two humans at explicit tiers0,1,2. Each cell uses a fresh browser context and storage. The original automatic startup classification is captured before the scripted manual tier choice. Thus a tier0 matrix cell is not evidence that a weak device automatically chose tier0. Lobby stays in the ordinary galaxy UI; other scenes enter using the current galaxy label, then use the existing world parameter path with seed49731. Spawn and water isolate zero bots; mixed-bot and two-human scenes request four mixed bots and record actual count because existing tier caps can reduce it. Each applicable scene drives for60s using the same bounded throttle and sinusoidal steering inputs through the existing input path. This is a scripted workload, not natural player or autonomous encounter frequency.

Raw collection starts at the composition root's existing assignment to window.syn3h, before game.start. The collector wraps the existing quality callback but never uses its eligibility decision to discard observations. Each record retains actual frame interval, visibility, scene phase, effective level/rung/settings/target, physics cost, renderer submission cost, draw count, triangles, position and population. It includes every frame over1000ms. Invalid intervals remain in the artifact and fail coverage. A hard100,000-frame cap marks overflow and fails acceptance instead of silently truncating a successful result.

Startup, transition, warmup and measured phases have separate summaries. The measurement window is60s for every scene, with five warmup seconds. A frame completing across a phase boundary is labelled by the phase at callback time; browser traces and explicit transition events provide the finer ordering. Hidden frames are retained and tagged. Main acceptance is for the host; a second human's full raw trace is preserved separately, including visibility, without claiming an obscured guest was foreground performance evidence. Per-phase summaries report p50,p99,max, all stalls over1000ms and counts above twice each frame's actual target interval. A measured cell passes only with nonempty finite visible evidence, no overflow, no renderer/setup errors and no frame exceeding twice target. Average FPS cannot pass this gate. The lowest supported tier is not claimed until its entire applicable matrix passes; higher tiers remain separately reported.

The runner records all renderer console errors and aborts remaining cells on renderer/setup failure. A budget failure is retained and the matrix continues, ending with exit2. Each cell has raw JSON and a Chrome trace; partial raw data is saved before trace export so export failure cannot erase observations. Original artifacts are never overwritten. Isolated ports, unique rooms and endpoint assertions remain; owned processes close after the run. No feature URL switches or extra GPU contexts/adapters are used.

## Pacing controls and withdrawn interval conclusions

A blank page in headless Chrome under the same flags and job wrapper paced at p50 67 ms and p95 133 ms (Lobby's control, relayed by Orchestrator). The browser was not delivering frames near 60 Hz with no game on the page at all. Every frame interval this lane recorded in headless runs without a control is therefore withdrawn as evidence of game speed or of any optimization benefit. That covers the baseline and matched profiles, the 52.6/142.5, 57.2/146 and 38.3/92.2 ms figures quoted below, and the elapsed crossing intervals from Water. The artifacts are kept and are labelled indicative and unqualified. Evidence that does not depend on pacing stands: CPU long tasks and profiles, pipeline and program creation counts, validation errors, draw calls and triangles. GPU timings count only where the backend actually supports them.

The runner now measures a blank-page control in the same browser session immediately before and immediately after every cell: three seconds of requestAnimationFrame gaps on a blank page that is alone and in front, before the game page opens and after it closes. Tracing is off during both controls, so they bound browser pacing and not tracing overhead. A control is valid when its median is within 20% of the expected refresh interval, its p95 is at most 1.5 times that interval, and it holds at least 80% of the frames the window should contain. The expected rate is 60 Hz unless PERFORMANCE_REFRESH_HZ states the display's rate for a headed run.

A cell's intervals qualify only when both controls are valid. Otherwise the cell's interval summaries are written under unqualifiedPhases, its phases field is null, its gate fails and the run exits 3. Nothing in an unqualified cell may enter an acceptance or report table; the raw frames stay in the artifact as invalid evidence. Exit 2 still means qualified cells missed their frame budget. Valid controls show the browser could pace at that moment. They do not make a loaded shared host equivalent to a phone, so pacing acceptance still needs a quiet headed run as the only heavy job, and the owner's devices.

## Diagnosis boundaries

Chrome tracing starts before navigation with timeline, user-timing, V8/GC and GPU categories. This covers initial module work and startup work before the per-frame collector exists. Runtime instrumentation times the existing render path, existing backend render-pipeline creation and existing texture-update submission calls. These counters do not measure asynchronous compilation completion, transfer completion or GPU execution. A timeline event's name or correlation is a lead, not proof of the dominant cause. Terrain/map generation must be tied to source stacks or existing startup measures; GC pauses must be identified by trace events; texture upload and compilation must be corroborated with their call/event timing. Missing trace categories or backend methods must be reported as unmeasured, not zero cost. Instrumentation itself can perturb results.

The previous matched profile is failed rendering evidence because it logged a WebGPU usage conflict, despite its process exiting zero. Its recommendation-filtered sample stream also omitted intervals over1000ms and cannot satisfy the raw stall gate. Root's existing desktop medians/p99 of52.6/142.5ms spawn,57.2/146ms water and38.3/92.2ms two humans are historical evidence only. No lower-tier or lobby acceptance follows from them. Requested reflection-map size64 is not actual allocation size: the installed Three PMREM clamps to at least256. Post Effects has since confirmed a Ripples source/destination alias on reallocation, as relayed by Orchestrator. This supersedes the earlier unassigned-cause note; the reflection allocation size alone was not causal evidence. Post owns the minimal reset and lifecycle/WebGPU/WebGL regression. The exact tested fix revision and raw Post evidence must accompany the next candidate; they have not yet been supplied to this lane.

## First-entry source audit

QualityController construction reads user agent, touch points and browser-estimated device memory, then applies saved/loading recovery state. initialize awaits the bounded adapter probe and classifies adapter availability/fallback plus maximum texture dimension; it applies the selected budget before game.init returns. main awaits game.init before creating terrain, attaches the selected terrain quality, builds the scene and only later calls game.start. Therefore the known device classification is available before the first ordinary world-loop draw. Some startup/offscreen work can occur before the world loop; it must be examined in the startup trace rather than called absent. The raw initial snapshot records deviceLevel, adapterProbe, actual settings, selected backend/hardware and firstFrameMs before the first callback. A fresh real device remains required to validate its actual detection and performance.

Current classification treats fallback adapters, texture limits below8192 or reported memory at most2GB as safe; mobile/touch hints normally select mobile, and unavailable adapters or reported memory at most4GB lower desktop classification. These are existing heuristic inputs, not benchmarks or promises. Unknown memory is not evidence of abundant memory. The idle display probe estimates a display/frame cap, not available GPU throughput. Reactive shedding needs observed slow windows and cannot prevent an unforeseen first shader compile, terrain rebuild, upload or GC stall.

Potential proactive inputs already available without probing include viewport/backing pixel count, selected backend/adapter limits, recovery history, chosen world recipe/size, selected effects and current vehicle/population requests. They can guide a separately reviewed conservative workload policy only after measured source-level costs support it. No new proactive policy or causal ranking is proposed from the loaded-host averages.

## Repeated water crossing and assignment audit

Each water cell additionally records a separate30s crossing fixture after its60s drive. It uses the existing cinematic-camera API at a deterministic point with at least8m of water depth, alternating requested camera height3m above and3m below the live surface every5s. Actual camera position, surface depth and rendered scene-node identity are recorded per frame, alongside requested transition events. These are staged camera transitions, not a claim about natural vehicle submersion. Crossing frames have their own strict twice-budget gate and remain in the raw artifact. A requested crossing that never produces the expected actual depth cannot establish acceptance.

Orchestrator relayed Water's baseline evidence: 25 createRenderPipeline calls on each tier 0 crossing across ten repeated entries/exits, with RAF intervals of 84 to 331 ms. This verifies repeated pipeline creation at crossings, rather than merely a suspicious fog assignment. Shared-host load limits interpretation of the elapsed times; call counts do not establish asynchronous GPU compilation duration or assign the whole stall to one operation. Exact Water source and artifact references remain pending. The permanent fog correction should be considered with the ripple fix for the same candidate before the full matrix runs.

## Automatic quality drops

For a quality change claim, record the world entry level, backend, active vehicle and each transition in order. Run the entire descent in one session from High, Ultra and Cinematic on each backend. The check feeds slow samples to the governor at wall-clock pace and records actual node builds and pipeline requests. It fails on a missed level, a browser error or any build during a drop.

Use a locally served production build with its room server. Run each cell through the shared heavy queue.

tools/heavy.sh node tools/quality-drop-check.mjs "$origin" webgl 3 high-webgl.json
